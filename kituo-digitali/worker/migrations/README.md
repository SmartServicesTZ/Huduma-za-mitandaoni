# SmartServicesTZ — Firestore to D1 migration work

## Current state and boundaries

Firestore remains the application's source of truth. Production handlers remain Firestore-backed; D1 is not wired into the production Worker. No Firestore records were read or copied, no production Worker or website was deployed or changed, and no production cutover was performed.

The only D1 target inspected or changed is the synthetic test database `smartservicestz-poc-clean` (`b2b331d9-fb25-416d-890a-269d07346faf`). The older `smartservicestz-poc` database is out of scope. Before the role migration, a full D1 SQL export was restored successfully into a fresh local-only Wrangler persistence directory. The backup is 7,927 bytes, SHA-256 `ea5584dd600b0a3b19f975ea8032588ac8b6e5de4c7ef7a9877abc9216ed2788`, retained outside Git as `SmartServicesTZ-poc-clean-pre-0002-2026-10-27.sql`, and contains only the confirmed synthetic PoC fixtures.

A comparison of the backup with migration 0001 found the same 33 application tables/indexes except for one known schema difference: remote `users.role` allowed only `user`, `admin`, and `super_admin`, while the checked-in schema supports `user`, `admin`, `moderator`, `support`, and `super_admin`. The existing synthetic rows exactly matched migration 0001's seed values, and the remote target had one user, one service, one token-balance row (NIDA=2/service=5), and zero rows in each other application table. No foreign-key violations were present.

To avoid replaying the already-existing schema blindly, the verified state was recorded as baseline `0001_smartservicestz_poc.sql` in a Wrangler-compatible `d1_migrations` table. Migration `0002_expand_user_roles.sql` was then applied only to this clean test database through a single Cloudflare D1 API batch of 47 statements. The journal now records both 0001 and 0002. Read-only verification found the five-role CHECK, 19 application tables, 14 explicit indexes, no residual migration staging tables, no foreign-key violations, and unchanged synthetic rows. A remote synthetic test inserted/read/deleted `moderator` and `support` users and confirmed zero temporary users remained. Wrangler CLI OAuth is still unauthenticated; the authorized Cloudflare API connector was used for this explicitly scoped test-database operation.

The remote backup file is a pre-migration rollback copy for this test database, not a production backup. It was restored and migration-tested locally; no remote restore or production backup/restore was attempted.

## Source-to-target mapping and decisions still required

These are recommendations for review, not adopted business rules. Keep Firestore authoritative until each mapping, access policy, and test is explicitly reviewed.

| Domain | Firestore behavior observed | Current D1 PoC coverage | Recommendation and effect; unresolved decision |
|---|---|---|---|
| Users, roles, permissions, restrictions | `users/{uid}` includes profile fields, role, permissions, `accountStatus`, `accessMode`, `allowedActions`, restriction notices and password-reset state. Current role set includes `user`, `admin`, `moderator`, `support`, `super_admin`. | The applied test schema supports all five role values; `user_permissions` stores individual permission rows. D1 user reads are read-only. Account restriction fields, password-reset state, and Firebase custom-claim synchronization are not represented. | Preserve role values without silently collapsing `moderator`/`support` into `admin`; define permission and restriction equivalence before wiring D1 authorization. Missing restriction/password/claim semantics still require a compatibility design; guessing could broaden access or lock users out. |
| Service catalog and CMS | Firestore collections include `services`, `siteSettings`, `announcements`, `tutorialVideos`, `serviceLocks`; catalog defaults and homepage ordering affect client behavior. | D1 has `services`, `site_settings`, `announcements`, `tutorial_videos`, `service_locks`; only a visible-service read helper exists. | Define per-collection field validation and explicit mappings for visibility, lock state, order, form fields, token cost, defaults, and initialization flags. Keep JSON payloads only where their version/validation contract is tested. Otherwise content can disappear, reorder, or behave differently. |

No balance precedence or conversion is chosen here; guessing could duplicate or erase token value. |

Refund, chargeback and ambiguous `CREATE_UNKNOWN` handling need business/provider decisions and cannot be inferred from the table schema. No live provider was contacted. |

Keep application, token debit, ledger and license issuance atomic where appropriate. The existing five-digit suffix and eligibility rules must not be changed without product approval. |

Do not copy file bytes or widen public access. Storage provider, retention, and deletion windows require approval. |

## Work completed in this branch

- `src/firebase-auth.ts` extracts the existing Firebase ID-token verifier without changing its RS256, issuer, audience or UID checks; synthetic local-JWKS tests cover acceptance and rejection cases.
- `src/d1-migration-checkpoints.ts` provides bound, state-idempotent checkpoint upsert/read and count/checksum comparison primitives for migration rehearsal. It records metadata only; it does not read Firestore or move application records.
- `migrations/0002_expand_user_roles.sql` rebuilds the isolated PoC `users` table while staging and restoring its dependent rows in FK-safe order. The migration contract test preserves 13 synthetic rows across 13 tables, accepts the five observed roles, rejects an unsupported role, and checks FK integrity.
- `scripts/d1-poc-schema-contract.py` validates all 19 PoC tables, 14 explicit indexes, documented constraints, five read-only repository SELECTs, checkpoint SQL, and the legacy-to-five-role migration using synthetic in-memory data.
- `scripts/order-d1-sql-for-restore.py` reorders SQL dumps so local statement-by-statement restore creates all tables and inserts parent rows before dependent rows. It refuses unknown SQL or FK cycles and never alters the original backup.
- `scripts/d1-poc-backup-restore-check.sh` exports only local PoC D1, reorders a separate restore copy, restores into a fresh local persistence directory, verifies both migration-journal entries and synthetic fixtures, and removes only its own temporary restore directory.
- Seven synthetic-only characterization suites cover current Firestore behavior for users/permissions, token adjustments, payment-pending webhooks, NIDA, Lipa, service applications/licenses, and audit/messages/FCM. They do not wire D1 or choose new business policy.
- `.github/workflows/worker-ci.yml` runs the schema contract, Worker tests, TypeScript, dry-run build, journal-aware local PoC migrations, fixture checks and local backup/restore. It uses read-only GitHub contents permission and no secrets.

## Safe local rehearsal

From `kituo-digitali/worker`:

```sh
pnpm test
pnpm check
pnpm d1:poc:schema-contract
pnpm build                     # Wrangler dry-run; does not deploy
pnpm d1:poc:migrate:local      # local sandbox only; applies tracked 0001/0002
pnpm d1:poc:verify:local
pnpm d1:poc:backup-restore:local
```

Every `:local` command pins Wrangler to `--local`. The recovery rehearsal retains the original local SQL export and restores a separately reordered copy into a fresh temporary local persistence directory. Remote export of the clean PoC snapshot has also been restored into a local-only directory. No remote restore was performed because it would overwrite the test database.
